# Design

## Context

The app's schema lives in `src/core/db/schema.ts` (12 synced tables plus the local `settings`), and its migrations are drizzle-kit SQL files in `drizzle/`. Their count is the schema version (`PRAGMA user_version`). All SQL goes through the small `SqlDriver` interface (`src/platform/db/driver.ts`), which has a `node:sqlite` implementation for tests. Timestamps are ISO 8601 UTC text from `Date.toISOString()`, so they compare correctly as text.

D1 limits that shape the API (Cloudflare docs, free plan): 50 queries per Worker invocation, where one `batch()` counts as one query and runs as one transaction; 100 bound parameters per statement; 100 KB per SQL statement; 2 MB per bound string; 500 MB per database.

## Goals / Non-Goals

**Goals:**
- Server logic testable with Vitest on Node, without Cloudflare tooling in the test run.
- The server schema cannot drift from the app's: one source for columns, and a test that fails when they differ.
- Every push and every pull is a single D1 batch, regardless of how many rows it carries.

**Non-Goals:**
- Running the tests inside the Workers runtime (`@cloudflare/vitest-pool-workers`). The SQL is plain SQLite, and the end-to-end check runs against `wrangler dev`.
- A client library for the API (comes with `sync-client`).

## Decisions

### Layout: `server/` beside `src/`, sharing the schema and the driver interface
```
server/
  wrangler.jsonc            Worker config: D1 binding DB, assets ../dist, run_worker_first /api/*
  worker-configuration.d.ts generated by `wrangler types` (committed)
  tsconfig.json             Worker types, server/src without tests
  migrations/               D1 migrations, generated by drizzle-kit
  src/
    index.ts                Worker entry: binds env (DB, DEVICE_TOKENS) to handleApi
    api.ts                  handleApi(request, deps): routing, CORS, auth, version check, errors
    auth.ts  push.ts  pull.ts  status.ts
    tables.ts               synced tables and their column names, from the app schema
    schema.ts               server Drizzle schema (only for migrations)
    d1-driver.ts            SqlDriver on D1
```
`api.ts` and the modules below it use only `Request`/`Response` and `SqlDriver`, so tests call `handleApi` with the Node driver. Only `index.ts` and `d1-driver.ts` touch Worker globals. Type checking: `server/tsconfig.json` (Worker types, no DOM, no tests) and the root `tsconfig.json` (which adds `server/src/**/*.test.ts`); `npm run typecheck` runs both. Vitest's `include` adds `server/**/*.test.ts`.

A separate npm workspace or package was considered. It is not needed for one Worker that imports two files from `src/`.

### One column source for app and server
`schema.ts` is refactored so each table's own columns come from a factory function (`columns.areas()` …, plus the existing shared columns). The app builds its tables from them as before, with its unique indexes. `server/src/schema.ts` builds the same tables plus `server_seq integer not null` with an index, and a `sync_state (id integer primary key, seq integer not null)` table. Factories, not shared objects, because Drizzle column builders should not be reused across tables. `SYNCED_TABLES` (name → table) is exported from the app schema. `server/src/tables.ts` derives each table's column names from it with `getTableColumns()`.
- Server tables keep the NOT NULL constraints (a bad row fails the batch → 400) but have **no unique indexes besides the primary key**. Natural-key IDs already make duplicates one row, and an extra index could reject a valid upsert.
- `npm run db:generate` must report no changes after the refactor, so the app's migration stays byte-identical.
- Drift test: apply `server/migrations/*.sql` to a Node database and compare `PRAGMA table_info` of every synced table with the app's columns plus `server_seq`. It fails when someone changes the app schema without running `npm run db:generate:server`.

### Change numbers instead of `server_updated_at`
Every stored row gets `server_seq`, a number from the counter in `sync_state`, increasing with every stored row. A pull returns rows with `server_seq > cursor`, and the cursor is the last returned row's number. This replaces SPEC §7's `server_updated_at` with "overlap": a counter changed inside the push transaction is ordered the same way commits are, so no change can be skipped and no overlap or re-applying is needed. Paging is also exact, with no ties. SPEC §4 and §7 need this wording update. Not an API concern for clients: the cursor stays opaque.

### Push: one upsert statement per table over `json_each`
Wire rows are objects keyed by **database column names** with stored values (`is_next_step: 1`, `weekdays: "[1,3]"`), so the server needs no mapping. For each table in the push, one statement with two bound parameters, whatever the row count:
```sql
INSERT INTO tasks (id, created_at, …, server_seq)
SELECT value ->> '$.id', value ->> '$.created_at', …,
       (SELECT seq FROM sync_state WHERE id = 1) + ?offset + key + 1
FROM json_each(?rowsJson) WHERE true
ON CONFLICT (id) DO UPDATE SET created_at = excluded.created_at, …, server_seq = excluded.server_seq
WHERE excluded.updated_at > tasks.updated_at
RETURNING id
```
The batch is `INSERT OR IGNORE INTO sync_state VALUES (1, 0)`, then one upsert per table (`offset` = rows of the tables before it), then `UPDATE sync_state SET seq = seq + <total rows>`. Ignored rows leave gaps in the numbers, which is harmless. `RETURNING id` returns only stored rows, so the response's `stored` is the sum (checked on SQLite 3.53: an upsert skipped by its `WHERE` returns nothing). Validation runs before any SQL: known tables, exactly the table's columns, `updated_at` and `created_at` matching `^\d{4}-\d\d-\d\dT\d\d:\d\d:\d\d\.\d{3}Z$`, at most 500 rows, a body of at most 1 MB (each table's JSON stays under D1's 2 MB per parameter). A constraint error from D1 is answered with 400. The batch is a transaction, so nothing is stored.

Alternative: one `INSERT` per row with bound values. A task has 14 columns, so a 500-row push would be 500 statements. That still fits in one batch but makes much larger requests, and it is no simpler.

### Pull: one batch of per-table selects
`SELECT <columns>, server_seq FROM <table> WHERE server_seq > ? ORDER BY server_seq LIMIT 1001` for each of the 12 tables, in one batch. The Worker merges the results by `server_seq`, takes the first 1000, sets `more` when there were more, and returns `cursor` as the last taken number (or the given cursor when nothing is returned). Rows are grouped by table and `server_seq` is left out.

### HTTP API
| Request | Response |
|---|---|
| `GET /api/status` | `{ "hasData": bool, "schemaVersion": n }` (`hasData` = counter > 0) |
| `POST /api/push` body `{ "rows": { "<table>": [row, …] } }` | `{ "stored": n }` |
| `GET /api/pull?cursor=<n>` | `{ "rows": { "<table>": [row, …] }, "cursor": n, "more": bool }` |

- All need `Authorization: Bearer <token>`. Push and pull also need `Orbit-Schema-Version: <n>`, and a missing or different value gets 409. Status does not need it, so an outdated device can still read the server's version.
- Errors are JSON `{ "error": "<message>" }` with 400, 401, 404, 409, 413 or 500. Every API response, preflights included, carries `Access-Control-Allow-Origin: *`, allowing `Authorization`, `Content-Type`, `Orbit-Schema-Version` and the methods `GET, POST, OPTIONS`. `*` is safe because nothing relies on cookies, and the token is always required.

### Schema version from the migration journal
`src/core/db/version.ts` exports `SCHEMA_VERSION = journal.entries.length` from `drizzle/meta/_journal.json`. A JSON import works in both Vite and wrangler's esbuild, while `import.meta.glob` works only in Vite. The Worker's expected version is therefore the app version it was built with. A test asserts that it equals the latest version of the bundled migrations.

### Device tokens
Secret `DEVICE_TOKENS`: comma-separated `name=token` pairs (`desktop=…,browser=…`). The names only make the list readable. The Worker hashes the presented token and each configured token with SHA-256 (`crypto.subtle`, in both Workers and Node) and compares the digests in constant time with a small XOR loop, so the check does not leak timing. `npm run server:token` prints a new random 32-byte base64url token. Adding or removing a device means `wrangler secret put DEVICE_TOKENS` with the new list. For local runs, `server/.dev.vars` (gitignored) holds the same variable.

### Serving the browser build
`assets: { directory: "../dist", not_found_handling: "single-page-application", run_worker_first: ["/api/*"] }`. Only `/api/*` reaches the Worker. Everything else is the built app, with `index.html` for unknown paths. The wildcard in `run_worker_first` must be checked with `wrangler dev` (the docs' example only shows an exact path), and the fallback is to run the Worker first for all requests and forward non-API paths to an `ASSETS` binding. sqlite-wasm's `opfs-sahpool` needs no COOP/COEP headers, so no extra headers are needed.

### D1 driver
`query` uses `prepare(sql).bind(...).raw()` (rows as arrays) or `.run()`. `batch` uses `db.batch()`, whose results are row objects, so they are converted with `Object.values` in select order. This is safe because server queries have no joins with duplicate column names.

### Scripts
| Script | Does |
|---|---|
| `db:generate:server` | `drizzle-kit generate --config drizzle.server.config.ts` (out `server/migrations`) |
| `server:dev` | `npm run build`, apply migrations to the local D1, `wrangler dev` (local D1 via Miniflare, http://localhost:8787) |
| `server:migrate` | apply D1 migrations to the remote database |
| `server:deploy` | `npm run build`, `server:migrate`, `wrangler deploy` |
| `server:token` | print a new device token |

All wrangler calls pass `-c server/wrangler.jsonc`. The D1 `database_id` in `wrangler.jsonc` is committed, since it is not a secret.

### New packages
| Package | Why |
|---|---|
| `wrangler` (dev) | Cloudflare's CLI: local Worker + D1, migrations, deploy, `wrangler types` (so no `@cloudflare/workers-types`) |

## Risks / Trade-offs

- [Device clocks decide the winner (§7)] → Accepted, as specified. The server compares only `updated_at`.
- [Free plan: 100,000 rows written per day] → One user writes far less. A first upload of the whole database counts once.
- [Tests run SQLite 3.53 on Node, while D1 runs its own SQLite build] → The SQL uses only long-stable features (`json_each`, `->>`, upsert, `RETURNING`). The end-to-end task runs the same requests against `wrangler dev`, which uses D1's engine.
- [Strict schema-version equality: the Worker and the apps must be upgraded together] → Intended (no column loss). Deploy the Worker together with the new app versions. Devices with the old version stop syncing and keep their data (`sync-client`).
- [A leaked token gives full access to the data] → Long random tokens, HTTPS only, one token per device so one can be revoked. Cloudflare Access can be added later (§2).
- [`run_worker_first` wildcard support] → Verified in a task, with the fallback above.

## Migration Plan

1. `npx wrangler login`, `npx wrangler d1 create orbit`, put the `database_id` into `server/wrangler.jsonc`.
2. Create tokens with `npm run server:token`, then `npx wrangler secret put DEVICE_TOKENS -c server/wrangler.jsonc`.
3. `npm run server:deploy`, which creates the tables on first run and serves the browser build at `https://orbit.<account>.workers.dev`.

Rollback: `wrangler rollback` to the previous Worker version. D1 migrations are forward-only, like the app's. The server holds no data until `sync-client` exists, so it can be deleted and recreated freely during this change.
